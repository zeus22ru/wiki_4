# Отчёт о реализации: визуальные источники в RAG и portable OCR

Дата: 07.10.2026. Проект: `wiki_4`. Основание: `docs/TZ_visual_rag_rapidocr_windows.md`.

Документ фиксирует, что реализовано, что проверено реальным запуском на этой
машине, что остаётся непроверенным и какие ограничения известны. Критерии, для
которых реального запуска не было (корпоративные материалы, XWiki-сервер,
чистая Windows), **не** объявляются выполненными.

**Статус на 07.10.2026:** portable OCR и vision-модель проверены реальными
вызовами; визуальная индексация включена в `.env` и разворачивается на **рабочем**
индексе (`KB_VISUAL_ENABLED=true`, `KB_VISUAL_INDEX_NAMESPACE=default`).

## 1. Что реализовано

### Извлечение (ТЗ §4, §5, §9)

Единый реестр адаптеров `core/document_extraction/` с общим контрактом
`ExtractionResult` (Source / Block / VisualOccurrence / Locator):

- `text` — `.txt`, `.md`, `.log`;
- `html` — DOM-порядок, `img`/`picture`/`source`, `srcset`, lazy-load, `figure/figcaption`,
  inline data-изображения, inline SVG, зачёркнутый (устаревший) текст;
- `docx` — обход тела в порядке документа, inline и anchored-рисунки, вложенные
  таблицы, изображения в ячейках, native-текст фигур, заголовки по стилям,
  колонтитулы учтены как второстепенные;
- `pdf` — текстовый слой (pdfplumber) + рендеринг страниц/сканов (pypdfium2),
  `page_fallback` при отсутствии рендерера;
- `pptx` — рекурсивный обход групп, таблицы, картинки, native chart data, заметки;
- `xlsx` — значения + формулы с кэшем раздельно, встроенные изображения, диаграммы;
- `image` — самостоятельный источник, кадры TIFF, выборка кадров GIF, SVG;
- `convert` — `.doc`/`.xls` через portable LibreOffice (fallback, если нет).

### Каталог, хранилище, ассеты (ТЗ §6, §7)

- `core/kb_catalog.py` — SQLite: sources / assets / occurrences / analyses /
  dependencies / generations; связи Source↔Asset↔Occurrence, GC-кандидаты.
- `core/visual_assets.py` — оригиналы по SHA-256 (шардинг), производные с
  `parent_asset_id`, атомарная запись, кэш анализа, staging, безопасное чтение
  (защита от traversal), GC с grace-периодом и dry-run.

### Portable OCR (ТЗ §8)

- `core/ocr.py` — `RapidOcrJsonProvider` (pipe/oneshot, `shell=False`, без окна на
  Windows, таймауты старта/распознавания, один retry, закрытие процессов),
  нормализация ответа в собственную схему, `FakeOCRProvider` для тестов.
- `core/imaging_utils.py` — растеризация SVG, тайлинг с перекрытием.

### Vision (ТЗ §11)

- `core/visual_analysis.py` — версионированный JSON-контракт, типы визуальных
  блоков, проверка графа схемы (уникальность узлов, endpoints связей,
  `uncertain` для неоднозначных стрелок), один repair, защита от инструкций на
  картинке (содержимое — данные, а не команды).

### Индексация и поиск (ТЗ §12, §13)

- `core/visual_indexing.py` — сохранение ассетов, OCR с кэшем, vision с кэшем,
  построение поисковых визуальных чанков (`chunk_kind=visual`, `evidence_kind=visual`,
  отдельные `text_raw` / `text_normalized` / `analysis_summary` / `embed_text`).
- `core/visual_pipeline.py` — конвейер для CLI/админ-reindex, preview-сводка,
  capabilities OCR/vision/рендерера.
- `create_vector_db.py` — визуальные чанки добавляются в общий индекс при
  `KB_VISUAL_ENABLED=true`; `scan_supported_files()` исключает `data/kb_assets`
  и `.tools`.

### Ответ и выдача (ТЗ §14, §16)

- `core/visual_context.py` — отбор occurrences по найденным визуальным чанкам,
  бюджет (группы/части/байты), тексты-маркировки `Визуальный источник V1`.
- `core/rag.py` — `RAGResult.images`; реальные байты изображений передаются в
  multimodal-вызов вместе с пользовательскими вложениями.
- `web_app.py` — `images` в JSON и SSE `done`, сохранение в metadata сообщения.
- `core/visual_serving.py` + `GET /api/documents/images/<occ>` — безопасная
  отдача original/preview/thumbnail, `nosniff`, ETag; маршрут не admin-only.
- `static/script.js`, `static/style.css` — галерея «Изображения из источников»,
  лайтбокс, ссылка «Открыть источник»; восстановление из истории.

### XWiki (ТЗ §10)

- `core/xwiki_assets.py` — скачивание ресурсов статьи через авторизованную
  сессию, `urljoin`, разрешение `%23`, lazy-load, оригиналы, валидация
  status/content-type, обнаружение login-формы, allowlist хостов, лимиты,
  sidecar-manifest без секретов.
- `scripts/parse_xwiki.py` — интеграция до публикации экспорта.

### Настройки (ТЗ §18)

Все ключи добавлены в `config/settings.py` и каталог админки
`config/settings_catalog.py` (группа «Визуальный RAG и OCR»), с типом, описанием
и допустимыми значениями. В коде `KB_VISUAL_ENABLED=false` по умолчанию
(безопасный старт); в рабочем `.env` функция включена явно.

### Тесты (ТЗ §22)

- `tests/test_document_extraction.py` — адаптеры (txt/html/docx/image).
- `tests/test_visual_rag.py` — каталог, хранилище, OCR, vision, визуальные чанки.
- `tests/test_visual_context.py` — отбор evidence, выдача изображений.
- `tests/test_xwiki_assets.py` — загрузка ресурсов с mock-сессией.
- `tests/test_ocr_windows_integration.py` — реальный portable EXE (пропускается,
  если комплект не распакован).

Итого: **476 passed, 1 skipped**. Unit-тесты используют fake OCR и mock
vision/HTTP; реальный EXE проверяется отдельным интеграционным тестом.

Вспомогательные скрипты:

- `scripts/rapidocr_manifest.py` — генерация `runtime_manifest.json` (хэши файлов,
  версии, активные профили, лицензии);
- `scripts/check_vision_model.py` — smoke-test поддержки изображений моделью
  (`--list` покажет список моделей, `--model <id>` отправит контрольную картинку).

## 2. Проверено реальными запусками

### Portable OCR

Portable-комплект **RapidOCR-json v0.2.0** (runtime-версия движка `1.1.0`)
распакован в `.tools/rapidocr-json/0.2.0/` и **проверен без сети**:

- one-shot (`--image=…`) и pipe-режим (`{"image_path": …}`) — оба распознают текст;
- формат ответа `{"code":100,"data":[{"box":…,"score":…,"text":…}]}` разобран;
- извлечены и включены в манифест хэши EXE/моделей/словарей; SHA-256 архива —
  `7ad9b283d03436c6cd0296723188699299cb4e5cf9140b410c59543aa5793c40`;
- добавлены лицензии компонентов (в архиве их не было);
- процессы корректно закрываются после использования (`_procs == {}`).

Обнаружено и учтено:

- кириллическая модель путает латиницу/цифры (номер ордера `00-00006695`
  читается как `Oо-Oооо6695`), поэтому реализован второй проход английской
  моделью с сохранением обоих чтений (`text_raw` + `text_raw_alt`);
- апстримный `cmd.txt` для English ошибочно указывает `dict_chinese.txt`;
  используется `dict_en.txt`;
- баннер старта содержит две служебные строки до JSON — они пропускаются.

Интеграционный тест `tests/test_ocr_windows_integration.py` прогоняется на этой
машине (реальный EXE, без сети) и проверяет, что точный номер `00-00006695`
присутствует в объединённом результате обоих проходов.

### Vision-модель

Провайдер чата (`https://api.deepseek.com`, OpenAI-совместимый) отдаёт две модели:
`deepseek-flash` и `deepseek-v4-pro`. Проверено смоук-тестом
(`scripts/check_vision_model.py`) и сквозным вызовом `VisualAnalyzer`:

| Модель | Изображения | Факт |
|---|---|---|
| `deepseek-flash` (модель ответов) | ✅ принимает | прочитала контрольный код `VISION 7391` дословно |
| `deepseek-v4-pro` | ❌ не принимает | ответила «не удалось прочитать изображение» |

Сквозной `VisualAnalyzer` на тестовой картинке-схеме вернул `status=success`,
`visual_type=flowchart`, корректные `visible_text` и `nodes` (`Заполнить`,
`Есть расхождения?`, `Проверить`, `btnOk`, `бпз_Заполнить`). Значит vision =
модель ответов работает, отдельная vision-модель не требуется.

> `deepseek-v4-pro` как vision использовать **нельзя**. Если он будет выбран для
> ответов, `VISUAL_CHAT_MODEL` всё равно надо оставить `deepseek-flash`.
> При отказе модели ответ не ломается: срабатывает откат с диагностикой
> `visual.fallback = vision_unsupported`.

## 3. Что реализовано, но НЕ проверено на этой среде

| Область | Причина |
|---|---|
| Корпоративные материалы (`ФМ Процесс …docx`, скриншоты 1С/Диадок/DataMobile) | Файлы не переданы в репозиторий |
| Живой XWiki (`http://wiki.bochkari.local`) | Нет доступа/учётных данных в этой среде |
| Portable LibreOffice рендеринг | Комплект не установлен |
| Чистая Windows без VC Runtime | EXE проверен на текущей машине; чистая среда — по ТЗ §22.6 |
| Качество поиска по визуальным фактам (top-5, ветви схем) | Пока не собран пилотный корпус и эталонная разметка (ТЗ §21) |

## 4. Известные ограничения

- `.ppt`, `.odt`, `.ods`, `.odp`, `.rtf`, `.vsdx`, CAD, аудио/видео не входят в
  первую поставку; реестр позволяет добавить их позже.
- Точное выделение области объекта из страницы офисного документа не всегда
  возможно — используется page fallback с пометкой происхождения.
- Vision-описание не является доказательством точного измерения; пиксельные
  оценки помечаются approximate.
- Проверка ответа (`verify_answer_against_sources`) для визуальных источников
  требует доработки: сейчас расширено хранение визуальных evidence, но
  отдельная проверяющая модель с картинками не подключена (ТЗ §15.3).
- Vision-модель = модель ответов (`deepseek-flash`), проверено — картинки читает.
  `deepseek-v4-pro` изображения не принимает. Если в будущем выбранная чат-модель
  окажется **текстовой**, vision-описания не строятся (статус `unavailable`), но
  приложение не ломается: ответ идёт по тексту с диагностикой
  `visual.fallback = vision_unsupported`, а изображения помечаются
  `used_for_answer=false`.
- Потоковый ответ передаёт изображения в финальном событии `done`; промежуточные
  дельты остаются текстовыми (в соответствии с ТЗ §16.1).

## 5. Безопасность и приватность

- Логи и манифесты не содержат cookies, паролей, токенов и base64.
- Маршрут выдачи изображений не принимает путь файловой системы; проверяется
  принадлежность хранилищу.
- Активный SVG не отдаётся inline.
- Содержимое источников трактуется как данные: текст-инструкция на изображении
  не становится командой модели.

## 6. Что передать для полной приёмки

Уже сделано: portable RapidOCR-json установлен (с `runtime_manifest.json` и
лицензиями); vision-модель определена и проверена (`deepseek-flash`).

Остаётся передать:

1. Корпоративные DOCX/PNG fixtures и доступ к XWiki (или равнозначные fixtures)
   для проверки ТЗ §20 и §21.
2. Доступ к чистой Windows x64 без VC Runtime для portable acceptance (ТЗ §22.6).
3. Список источников для пилотного корпуса и эталонную разметку (для метрик
   top-5 и качества ветвлений схем).

## 7. Проверка на рабочем индексе (как воспроизвести)

Всё настроено в `.env`; последовательность:

1. Убедиться, что сервер эмбеддингов и ключи живы (нужны для переиндексации).
2. Полная переиндексация — она же добавит визуальные чанки в рабочую коллекцию:

   ```powershell
   .\.venv\Scripts\python.exe create_vector_db.py
   ```

   Это пересобирает коллекцию `CHROMA_COLLECTION_NAME` целиком (текст + визуал).
3. Проверить в UI: вопрос по факту, который есть **только на картинке** → под
   ответом должна появиться галерея «Изображения из источников».
4. Диагностика: `GET /api/documents/images/<occurrence_id>` отдаёт изображение;
   в preview документа есть блок `visual` (число блоков, occurrences, доступность
   OCR/vision/рендерера).
5. Откат: `KB_VISUAL_ENABLED=false` и повторная полная переиндексация (или возврат
   коллекции/манифеста из бэкапа). Исходные документы не удаляются.
