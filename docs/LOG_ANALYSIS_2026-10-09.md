**Ключевой момент:** JSON-записи `llm_exchange` (`stage: retrieve | prompt | answer | final`) пишутся
**внутри `wiki_qa.log`** строками вида
`INFO | llm_exchange | _safe_json_log:146 | {"ts": ...}`. Из них удобно доставать вопрос,
ответ, латентности и скоры через `ConvertFrom-Json` от первого символа `{`.
В отдельный `logs/llm/llm_exchange.jsonl` за этот день ничего не попало — **это расхождение стоит проверить**.

**Ловушки окружения (PowerShell 5.1):**
- `Get-Content` по умолчанию читает файл как ANSI → кириллица превращается в мусор. Использовать
  `Get-Content -Encoding UTF8`; писать — через `[IO.File]::WriteAllLines(..., UTF8Encoding($false))`.
  Файл уже корректный UTF-8, «лечить» кодировку cp1251→utf8 не нужно.
- `[IO.File]::ReadAllBytes` иногда падает `IOException` (файл занят запущенным приложением) —
  читать через `FileStream` с `FileShare.ReadWrite`.
- Строки содержат ANSI-коды цвета → снимать `-replace '\x1b\[[0-9;]*m',''`.
- Формат строки: `YYYY-MM-DD HH:MM:SS | LEVEL | logger | func:line | текст`.

## 5. Выявленные дефекты и точки входа

### D1. Механизм цитат почти не работает (главная находка)

**Симптом.** `citations_count = 0` в 4 ответах из 5. В Q4 — только 1.

**Доказательства из лога:**
```
rag | extract_citations:1416 | Цитаты не найдено. Проверено предложений: 0/9
rag | extract_citations:1416 | Цитаты не найдено. Проверено предложений: 0/8
rag | extract_citations:1378 | Извлечение цитат завершено за 0.028 сек. Найдено цитат: 0
rag | enrich_answer_with_citations:2578 | Найдено цитат: 0, источников: 5
```
Счётчик `found_count` всегда остаётся `0`, т.е. ни одно предложение документа не считается
содержащимся в ответе.

**Точки входа:**
- `core/rag.py:1383` — `_find_citation_in_answer()`
- `core/rag.py:1416` — debug-лог «Цитаты не найдено»
- `core/rag.py:1326` — `extract_citations()`
- `core/rag.py:1419` — `format_answer_with_citations()`
- `core/rag.py:2518` — `enrich_answer_with_citations()`

**Причина (гипотеза).** Поиск цитаты — точное вхождение **целого нормализованного предложения**
документа в текст ответа (`normalized_sentence in normalized_answer`). При этом:
- документ режется по `[.!?]+`, что ломает предложения при сокращениях/инициалах/нумерации
  («1С:Документооборот», «02.04», «н11→n17» — точка внутри);
- LLM перефразирует, поэтому точного вхождения нет почти никогда;
- в тексте документа остаётся markdown/переводы строк, а ответ содержит разметку `**…**`.

**Рекомендация.** Заменить exact-substring на нечёткое сопоставление: нормализовать обе стороны
(убрать markdown/`«»`/ё→е, схлопнуть пробелы), считать пересечение шинглов/токенов и/или
посимвольное сходство (`difflib.SequenceMatcher` / `rapidfuzz`), порог подобрать на реальных парах
«документ ↔ ответ». Плюс исправить сплиттер предложений (использовать не только `[.!?]`, но и
защиту от «1С», «02.04», «ЭД №…»).

### D2. Долгие ответы: deep-retrieval не сходится и уходит в `max_iters`

**Симптом.** Q3: поиск 30,7 с, полный ответ ~46 с. Q4: поиск 22,8 с.

**Доказательства:**
```
Deep retrieval остановлен: max_iters
Deep retrieval завершён: iters=4, final_docs=5, best_score=0.732, queries=13, latency_ms=30699
Deep retrieval завершён: iters=3, final_docs=5, best_score=0.836, queries=10, latency_ms=22809
```
Сравните с «хорошими»: `iters=1, best_score=0.964, latency_ms=6347`.

**Конфигурация (действующая считается из overrides, а не из `.env`):**
- `data/settings_overrides.json`: `DEEP_RETRIEVAL_ENABLED=true`, `DEEP_RETRIEVAL_MAX_ITERS=4`,
  `DEEP_RETRIEVAL_MIN_BEST_SCORE=0.8`, `RAG_MULTI_QUERY_ENABLED=true`
- `config/settings.py:186–194`: дефолты `MAX_ITERS=3`, `MIN_BEST_SCORE=0.55`
- В `.env` (строки 181–188) все `DEEP_RETRIEVAL_*` **закомментированы** — фактически управляет только JSON.
- `core/rag.py:1045` — `retrieve_documents_deep()`, `:1063` max_iters, `:1065` stop_best, `:1164` условие остановки.

**Проблема.** Порог `stop_best=0.8` довольно высок: для «широких» вопросов (Q3) скор не дотягивает,
и система делает 4 итерации × 3 новых запроса = 13 запросов эмбеддингов — линейный рост латентности
без прироста качества (best_score падал: 0.726 → 0.732 → 0.667 → 0.657).

**Рекомендация.** (а) не продолжать итерации, если best_score **не растёт** (сейчас рост
остановился на 2-й итерации, но цикл работал до 4-й); (б) добавить общий бюджет времени retrieval
(например, hard-cap 8–10 с) с возвратом лучшего набора; (в) рассмотреть `MIN_BEST_SCORE` в диапазоне
0.70–0.75 как компромисс.
